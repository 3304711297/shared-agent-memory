2026-09-16，用户在 workbuddy2api 里加了一条前端说明文案（中文，位于 HTML/JS），我在验证新构建的 exe 是否包含它时，直接在 exe 字节里搜了那串中文——**命中 0 次，于是报「❌ 未进包」**。实际上改动**确实进包了**：前端资源被 **brotli 压缩**后嵌入，明文搜不到是必然的。

**规则（按区域选判据）**：
- **未压缩区**：Rust 侧字符串字面量、资源文件名（asset manifest 里的 `index-XXXX.js`）、结构体字段名等 —— 可直接在二进制里 ASCII/UTF-8 搜，命中即证据。
- **压缩区**：前端 bundle 里的中文/英文文案 —— 在二进制里搜**一定**是 0，**不能**据此判断缺失。要验文案，请读打包前的 `dist/assets/*.js`（或对应源文件）。
- **判「产物是否合格」用整体指标**，不要靠搜字符串：尺寸需**显著大于**已知的坏产物（本项目坏产物 = 无前端空壳，比好产物小约 68KB）；且必须用**能带上前端的方式**构建（tauri CLI 专有 feature，裸 cargo 会静默产出空壳）。
- **尺寸数值本身就是漂移的**——每加一个功能都会变（本项目本轮从 15,641,088 变成 15,663,616）。不要把某个具体字节数当判据写进文档/技能，写「比坏产物大」这个**关系**，或每次重新推导。
- **资源 hash 不能当新鲜度判据**：本项目 `vite.config.js` 把 git hash + 构建日期注入 fingerprint，每次构建都漂移。
- **判断「跑的是不是新版本」**另有硬指标：进程 `CreationDate` 晚于 exe 的 mtime。

**Why:** 我把「搜索无命中」直接读成「改动缺失」，方向完全反了（真实情况是搜索方法无效）。这类错误的代价是让用户白重建一次。**先问「我搜的这块区域是不是被压缩/编码过」，再决定用什么判据。**
