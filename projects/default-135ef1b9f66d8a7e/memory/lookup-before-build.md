# 先检索再造轮子（Lookup-Before-Build）

**铁律：在自行实现任何解析、签名、抓取、协议适配或样板代码之前，必须先检索是否已有成熟方案；严禁把「手搓」当作默认动作。**

## 触发场景

任一命中即适用：

- 要写签名/验签、加密、编码、正则解析之类「看起来有标准答案」的算法；
- 要适配第三方平台的私有接口、私有协议或反爬逻辑；
- 要写数据格式转换、导入导出、迁移脚本；
- 即将写出超过约 50 行「与业务逻辑无关的胶水代码」；
- 遇到陌生的报错码 / 风控码 / 限流码，正准备靠调参数试出来。

## 必查的三个来源（按优先级）

1. **本机已装技能池**——Skill-First Rule 的延伸，先 `skills_list` / `skill_view`，别重复造已封装的轮子；
2. **官方文档与官方 API 文档**（`web_search` / `web_extract`）——确认字段语义、限额、已废弃接口；
3. **成熟开源实现的源码**（GitHub 仓库源码，不只是 README）——看社区如何绕过同一个坑，常能直接得到正确参数组合或「此路不通」的结论。

## 反例判据（出现任一即停下来检索）

- 同一问题已换过 3 组参数仍失败；
- 正在依据「社区传闻」而非文档调参；
- 准备写超过 50 行与业务无关的胶水；
- 解释不清正在对抗的字段 / 错误码的官方语义。

## 实战案例（2026-09-13，B 站看门接入）

为绕过 `code=-352 风控校验失败`，连续试了伪造 buvid3、经 `finger/spi` 换取真实 buvid、多组请求头组合、以及动态接口——全属「手搓猜参数」，一轮下来毫无结论。用户叫停后一次检索即拿到决定性证据：

- bilibili-api-python 官方文档明写「**可使用代理，绕过 b 站风控策略**」；
- RSSHub 的同一路由源码要求 `getCookie()` + wbi 校验串，且 README 标注**反爬严格**，公共实例实测被 Cloudflare 挡 / 需 Playwright。

结论：该风控**靠调参数解不掉，只能换出口 IP 或换接口**——这才是真正的答案，手搓方向从一开始就是错的。

**Why:** 手搓的成本不是行数，而是**方向成本**。在错误假设上迭代会消耗大量轮次，且得出的结论不可信（不知道是方案错还是参数没调对）；成熟方案已过社区大规模验证，还能顺带给出边界条件与已知缺陷。「先检索」不是省事，而是避免朝错误方向白烧一轮。

**How to apply:** 动手前先花一次 `web_search`（或读官方文档 / 参考实现源码）。有结果则优先复用其思路与参数，只写业务差异部分；无结果则**写明「已检索 X/Y/Z 未找到现成方案」再手搓**，让「为什么自研」有据可查，而不是一次沉默的省略。
