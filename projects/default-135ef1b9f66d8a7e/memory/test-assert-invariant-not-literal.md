2026-09-16，workbuddy2api 修对比度时写契约测试（`tests/test_text_contrast_contract.test.js`）。两种写法差别很大：

**写法 A（锁字面量，脆弱）**：断言 CSS 里出现 `--text-muted: #77879d`。
问题：把色值换成另一个同样合规的色（如 `#8593a8`）会**误报失败**；而真正的不变量（对比度达标）反而没被断言——有人把变量改回 `#64748b`，只要同时改了断言的期望值就能绕过。

**写法 B（锁不变量，采用）**：断言「`--text-muted` 在其最坏背景上对比度 ≥4.5」。
- 换任何合规色都不误报；任何不合格改法都变红。
- 三个关键设计：① **取最坏背景**——深色用卡片 `#181c24` 而非更深的 app 底 `#0d0f12`（若用后者，卡片区域的不足会被掩盖，**这正是原缺陷能长期存在的原因**）；② 附带**前提断言**——背景真值若被改则要求重算，避免测试前提静默失效后仍在跑；③ 同时锁**关系型不变量**——`--text-muted` 必须弱于 `--text-secondary`，使「把 muted 提亮到与 secondary 同值」这种能达标却压平设计语义的**假修复**变红。
- 变异验证 4/4 全抓到（两个 muted 回退 / 提亮压平层级 / 日志色回退）——注意第 3 个变异只有关系断言能抓，纯阈值断言放它过关。

**Why:** 修复的目标是「性质」不是「实现」；把实现细节写进断言，既会在合法重构时误报，又会在性质被破坏但实现恰好没变时漏报。而「用最坏输入」是同一原则的一部分：用平均/典型输入测，等于假设最坏情况不存在，测试绿灯反而给了假信心。

**How to apply:** 写完断言先自问两句——「换个合法实现，它会误报吗？」「把同一不变量换个方式破坏，它会漏报吗？」两个答案都应是「不会」。其次检查测试输入是否取到**最坏情形**（最大/最小/边界值，而非中间值），并对外部真值加前提断言。最后做变异验证：手工把源改回缺陷形态，测试必须变红；若某个变异没被抓到，说明该性质未被覆盖。参见 [[audit-count-is-not-impact-scope]]（同轮教训：影响面要按真源重算）。
