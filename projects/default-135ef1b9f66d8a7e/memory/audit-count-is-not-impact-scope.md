2026-09-16，workbuddy2api 收尾「审计遗留最后一项」时踩到：审计报告说「3 处小字对比度不达标」（`.page-desc` / `.log-console-hint` / `.brand-subtitle`），我据此准备按 A 方案「只改这 3 处」。动手前顺手按「变量 + 全部使用点」重算，发现真实影响面是**深色主题 8/8 全不达标**（最坏 3.59:1）、浅色 4/8（最坏 4.19:1）——根因不在那 3 处写错色值，而在共享变量 `--text-muted` 本身的取值。若按原计划只改 3 处，会剩下 5 处（`.status-details` / `.metric-label` / `.quota-unit-tag` / `.agent-path-text` / `.usage-chart-axis`）照样不达标，而「审计项已闭环」的结论会让人以为修完了。

**Why:** 审计/体检类报告天然按**表现点**枚举（「这几个元素有问题」），而缺陷往往有**共同真源**（CSS 变量、公共样式类、共享工具函数、统一配置项）。按表现点逐条修，修的是症状且必然漏项；共享真源一处不合格，其名下所有使用点一起不合格，但报告不会替你展开这层。用「N 处」当工作量与完成度，等于用抽样结果冒充全集。

**How to apply:** 拿到任何「N 处有问题」的清单后，先做一步归因再动手——把每个待修点反查其**取值来源**，若多个点共享同一变量/类/函数/配置，立即改按「真源 × 全部使用点」重新枚举并重算影响面（本例：`grep 该变量 → 8 个使用点 → 逐点按其真实背景算对比度`）。修复落在真源层（改变量取值）而非表现点层（改 3 个选择器）。同时警惕**假修复**：把共享变量直接提亮/调暗到与相邻层级同值，能让指标达标却压平设计语义——所以契约测试要同时锁「达标」与「层级关系」两个不变量（见 [[test-assert-invariant-not-literal]]）。

**推论（同类场景）**：性能问题同理——「3 个接口慢」要反查是否共用一个连接池/中间件/序列化层；依赖漏洞同理——「5 个包有 CVE」要反查是否同源于一个被传递依赖拉进来的老版本。凡「多点同症状」先归因到真源，再谈修复面。
