# huggingface-chinese-plus 上游词库同步：故障模式与处置

## 仓库定位

- 油猴脚本（userscript）把 huggingface.co 界面中文化；`sources/hf-dict.json` 是**vendored 的上游词库快照**（上游 `izhadu/GreasyFork` 的 `HuggingFace-Chinese/dict.json`），`sources/hf-supplement.json` 是自有补充词库（优先级更高、永不被上游冲掉）。
- `.github/workflows/upstream-sync.yml` 每 6 小时跑 `scripts/check-upstream.mjs`：退出码 0=无更新、10=快照已更新（触发重建+测试+自动提交）、20=仓库自身状态异常（必须变红）。
- 上游不可达时脚本降级为「继续用本地快照」，工作流保持绿色——**上游挂掉不会变红，上游改规则才会**。

## 故障模式：上游改了规则数组 → 卡死在测试门，快照永远合不进去

`tests/regex-rules.test.mjs` 有两层保护，且**按数组下标绑定**：

1. 全规则数组（上游 + 补充，按 build 同序）的 sha256 稳定指纹 vs 文件里的 `BASELINE_HASH`；
2. `SAMPLES`：`#N → {pos, neg}`，要求**每条规则**都有正例/反例，用 `rules[N]` 直接索引。

因此上游只要**插入或删除**规则，N 之后全部错位：指纹红 + 从插入/删除点起成片「正例未命中/反例误命中」。工作流在「重新构建并校验」步骤就失败，**后面的自动提交不会执行**，于是每 6 小时重复：拉到新快照 → 重建 → 测试红 → 丢弃 → 下轮再来。表现为同一 commit 的定时任务连续红，但代码没有任何变化。

判据：失败日志里出现
`✖ 规则数量与内容与基线一致` + 从某个编号起连续的 `rule #N: 正例命中,反例不命中`，且 `check-upstream` 步骤退出码是 10（不是 20）。

## 处置步骤（按顺序）

1. **走真实同步路径**，不要手工覆盖快照：本机直连 `raw.githubusercontent.com` 会 DNS 失败，需让脚本内部的 curl 走本机代理（`HTTPS_PROXY` 前缀，端口见环境笔记）。成功时打印 `检测到更新: 词库 vA → vB,buildNumber → N` 并退出 10。
2. **比对规则数组**：按 `(pattern, replacement)` 做序列对齐，得出「删除区间 / 新增区间 / 可原样保留的规则」。不要凭条数猜。
3. **重映射 SAMPLES**：对旧样本按**规则身份**（不是下标）在新数组里找位置；被上游删除的规则连同样本一起删。
4. **为新增规则补写正例/反例**：正例必须命中且产出与原文不同；反例必须不命中——反例要挑同族近邻（单复数、有无锚点、`Page 2/10` vs `Page 2 of 10`），否则测不到串扰。
5. **重算 `BASELINE_HASH`**（用测试文件里同一套 normalize + sha256 口径），跑 `node --test tests/*.test.mjs` 直到全绿。
6. `node build.mjs` + `node --check`；**重算词库规模口径**（`buildIndex(translations).size` + 两数组长度之和），同步更新 README 与 `build.mjs` 注释里的数字。
7. 提交信息沿用工作流口径：`chore: 同步上游词库 v<版本> 并重新构建 (build <N>)`，正文写清删了/加了哪几族规则。
8. 收尾验证：再跑一次 `check-upstream.mjs` 应输出「无更新 (exit 0)」——证明下个定时任务不会重红。

## 2026-11-20 实例

- 上游 `2026.09.28 15:30:00` → `2026.11.19 14:45:00`，buildNumber 6。
- 删除 36 条**宽松日期规则**（`\bJan 5\b`、`5 Jan 2026`、`^January 2026$` 三族），新增 24 条 UI 文案规则（分页/卡片/计数/价格/`Config (N)` 等）。
- 规则总数 125 → 113；静态词条 1785 → 1897。89 条旧样本按身份保留，24 条新增规则补写样本。
- 决策（2026-11-20 已落地）：上游删掉的 36 条日期规则补进了 `sources/hf-supplement.json`（永不被覆盖），规则总数 113 → 149；README/`build.mjs` 口径同步为 1897 静态词条 + 149 正则，样本与基线指纹已重算。

## 通用教训

**把测试样本绑定到数组下标，等于把「上游加一条规则」变成「全文件红」**。改动这类索引耦合的测试时，要么改为按规则内容(哈希)绑定，要么把「重映射」写进同步脚本，让同步本身产出样本映射，而不是靠人每次手工对齐。
