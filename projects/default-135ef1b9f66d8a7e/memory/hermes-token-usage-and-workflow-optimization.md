# Hermes Token 消耗实测定性与工作流匹配分析（2026-09-08 实测）

## 背景与触发

社区（@HermesWatcher 等）讨论「哪些配置能最大化降低 Hermes 的 Token 消耗」。经实机挂载网关中立账本（`usage.db`）与 Hermes 状态库（`state.db`）比对实测，得出一组与常识反直觉但符合当前用户高频长上下文工作流的关键定性。

## 实测核心发现

### 1. 为什么 proactive_prune / 提前压缩不适合当前工作流

- **用户行为特征**：习惯单会话承载高密度调试、代码分析，会话在 50 万至 100 万 token 左右完成阶段性目标后直接删除/归档，从不长期维持单一会话。
- **Prune 的副作用（代价倒挂）**：
  1. 每次 prune/提前压缩会导致已建立的 Prompt Cache 前缀失效（上游 Issue #91830）。
  2. 在 Gemini / Antigravity 缓存读取倍率接近免费或极低的计费模型下，为了剪枝而引入的多次摘要计算与缓存前缀击穿，在费用面上完全倒挂。
  3. 剪枝保住的「长期上下文余量」对于 1M 即删的短周期会话没有实际价值，反而容易丢掉刚刚执行过的文件细节。
- **结论**：维持出厂默认 `proactive_prune_tokens: 0`，不擅自开启。

### 2. 已兑现的有效优化：background_review 关闭

- **实测账本取证**：
  - `state.db` 中 `session_model_usage` 明确记录：`background_review` 任务历史占总调用次数的 17.8%，但因每次触发均需重读完整会话上下文，吃掉了 **37.5% 的 Cache Read Tokens**。
  - 其单次平均读量高达 133,781 tokens（是普通主会话交互的 2.7 倍）。
  - 2026-09-07 配置 `auxiliary.background_review.enabled: false` 后，09-08 全天调用数为 0，会话平均每次调用的 Token 消耗直接下降 **22.8%**。
- **结论**：关闭后台自动审查是性价比最高且完全不伤主流程质量的单一杠杆。

### 3. 反直觉防护：严禁关闭 tool_search

- 部分用户误以为禁用工具能减小体积，但 Hermes 的 `tools.tool_search` 渐进式披露机制已将 123 个不常用/MCP 工具（约 38.5k schema）隐藏在 4k 目录之后。
- 每轮固定底座消耗仅约 21.7k（含系统提示词与直出核心工具）。关掉 `tool_search` 反而会导致工具全量展开，每轮暴增 31k+ tokens。

### 4. 社区实践对照

推文回复中高赞实践同样证实：
- 核心省流方式在于**前端精简（Bot 专用化、按需分发技能与 MCP）**，而非靠后端的激进压缩。
- 外部 CLI 代理（如过滤冗余终端输出）可显著降低每轮历史膨胀速度。
