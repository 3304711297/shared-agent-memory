2026-09-16，workbuddy2api 用户反馈：「我开了仅展示可用模型，但模型列表里还是有需授权模型」。排查结论：**开关没坏**——内核 `/v1/models` 实测已过滤（36 项、需授权模型 0 项）。用户看到的 42 项来自**客户端自己配置文件里写死的静态清单**（该客户端 `discover_models: false` 时从不请求本清单）。

**规则**：
- 设置的**作用范围跨进程边界时**，边界本身就是必须写进 UI 的信息：说明它管什么、不管什么、对端要改哪个开关、改完是否需要重启。否则用户只能在错误的开关上瞎试，并把结果报成缺陷。
- **把说明挂在开关旁边**（而不是塞进帮助文档），并让它**随当前选择变化**——提示要出现在错误预期最可能发生的那一刻。
- **绝不写代码做不到的承诺**。本例若写成「选此项即可让客户端隐藏该模型」读起来更顺，但那是假承诺（客户端是否采用清单由客户端决定）。宁可如实写清范围（「此开关只改变本工具对外提供的清单」），也不给以后还会踩的保证。
- 写测试时**加一条反向断言**，防止后人把误导性承诺写回去。契约测试同时锁「必须提到对端开关」与「不得出现误导措辞」。
- **复用样式前先确认类存在**：本例我照直觉写了 `notice-box` / `notice-info`，查了才发现这三个类在样式表里根本没定义（会渲染成无样式裸文本）。HTML/CSS 成对 grep 只要几秒。

**另一个教训**：用户提出「重新添加端点会不会好」时，要分清**客户端侧操作**与**软件侧缺陷**——本例显示异常属软件侧检测/提示缺失，重装端点改不了，且删除操作还有切断在用链路的风险。要明确劝阻并给出真正的步骤。
