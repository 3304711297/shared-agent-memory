# 多仓治理、并发调度与双发布通道实战踩坑教训

2026-09-08 针对全账户 9 个公开仓库完成一轮深度审计与加固落地，期间暴露了 5 个典型的认知偏差与执行陷阱，特此复盘并固化长效防范约束。

---

## 核心教训与反模式剖析

### 1. 多独立任务串行下意识惰性（严重违背 Fork-First 铁律）
- **错误表现**：面对四个仓库（make-bilibili / openrouter / huggingface / steamdb）的 Actions 钉版与通道加固任务，主会话一度出现单线程串行处理的动作，被用户当场纠偏。
- **根因分析**：模型思考时容易陷入“规划一个接一个做”的局部直觉，在拆解完多仓任务后没有在第一反应强行刹车并触发 `delegate_task` 并发调度。
- **防范铁律**：**只要用户输入或工程拆解包含 2 个及以上相互独立的诉求（如跨仓库改造、独立模块加固、多目标分析），第一动作必须坚决直接调用 `delegate_task` 进行并行分派**，严禁在主会话单线程串行起跑；主会话永远保持调度响应与收尾聚合。

### 2. 版本号基线凭空推论（严重违背 Fact-Checking 实证铁律）
- **错误表现**：面对无历史 Git Tag 的仓库，凭经验假设“从 v1.1.0 或 v1.2.0 起步”，忽视了代码与构建产物中 `@version` 实际早已是 `1.3.3` 与 `1.4.4`，险些导致严重的版本倒退与油猴更新判定失效。
- **根因分析**：未在第一时刻使用 `read_file` 查验源文件与产物头部的真实声明，把“缺乏 tag”错误推断为“代码版本低”。
- **防范铁律**：**严禁凭经验或历史讨论推测版本号与配置基线**。在制定版本计划前，必须优先读取实物文件的真实声明（`package.json`、`build.mjs` 以及产物头部的 `@version`）；任何新发布的 Release Tag 必须严格顺延现有产物的最高版本（单调递增）。

### 3. 发布通道“纸面闭环”与油猴静默覆盖陷阱
- **错误表现**：README 宣称已建立 Stable 稳定发布通道，但仓库根本没有 `release.yml` 自动化工作流、Releases 链接为 404，且 `build.mjs` 中 `@downloadURL` 与 `@updateURL` 硬编码指向 `main` 分支。若用户真从 Release 安装，首次检查更新便会被 Tampermonkey 强行覆盖回滚动 `main`。
- **根因分析**：只停留在修改文档说明，未沿着用户从安装到自动检查更新的真实物理链路穿透构建产物代码。
- **防范铁律**：油猴脚本建立多通道时，构建逻辑必须在代码层解耦（如 `build.mjs --channel=stable`）；稳定版产物的 `@updateURL` 必须显式绑定 Release 直链；且必须配齐 `release.yml` 并在打 Tag 后实测发布物真实可达，杜绝纸面闭环。

### 4. 公开仓库脱敏仅改表面（漏报全仓全局硬编码）
- **错误表现**：初轮脱敏仅修正了 README，未意识到全仓有 33 个已跟踪文件深层硬编码了开发机用户名。
- **根因分析**：依赖肉眼抽查而非全仓自动化审计脚本。
- **防范铁律**：公开仓库防泄漏必须依靠自动化门禁。全量已跟踪文件统一纳入 `check_hygiene.py`，并在 GitHub Actions CI 中作为前置门禁，对真实用户名、物理绝对路径与敏感 Token 进行零容忍拦截。

### 5. 配置文件环境变量化时的代码解析脱节
- **错误表现**：试图直接修改 `capability-inventory.json` 中的绝对路径为 `%USERPROFILE%`，险些破坏 Python 脚本解析与底层 `git -C` 子进程调用。
- **根因分析**：先改数据、后想逻辑，未意识到 Windows 下 Python `open()` 和底层 `CreateProcess` 默认不展开环境变量。
- **防范铁律**：涉及配置文件语义变更时，**必须先在代码解析层实现 `normalize_local_path` 兼容与单元测试验证**，测试绿灯后方可修改数据文件。

---

**Why:** 多仓工程与公开仓库治理极易因局部直觉或经验推论产生“看起来做完了、实际链路断开”的技术债。实证求真、全链路贯通与并发优先是保障质量的底线。  
**How to apply:** 后续任何多仓操作、版本发布与记忆维护，严格对照上述 5 项防范机制执行。
