## 外部 AI 评审（ChatGPT / Claude / 其它模型）的实证复核

评审意见是**线索**，不是结论。三条铁律：

1. **逐条回源码验证，不盲从也不盲拒。** 说「有 bug」的，找出那条代码确认；说「方向该这样改」的，先判断它对**本仓库**是否成立。本轮 5 个设置字段的指控全部属实（读盘回灌 cache），但评审同时漏了 2 个真根因（路由拼错 404、token 预算被思考吃满）——那是自己复现挖出来的。**只按评审清单修 = 修一半。**
2. **先复现再动手。** 评审描述的失败现象，必须自己打出同样的错误（curl / 探针 / 日志时间戳对齐）。复现不了就别改。本轮靠 `converter.log` 里 `22:26:31 finish=length tokens=119` 与截图 2759ms 精确对上，才确认「不是协议坏了，是预算饿死正文」。
3. **契约测试只证明代码形态，不证明功能生效。** 改完必须端到端实测：密钥改走环境变量后，用生产同款解释器起临时实例，实测「无头 401 / 正确 200 / 错误 401」才算修好。

### 主动构造反向对拍（决定「改不改」的关键一问）

评审通常只描述**单向**风险：「A 有值时会出现 B 副作用」。在判断要不要改之前，先构造**反向场景**再测一次——真正决定是否要改的往往不是评审点出的那一侧，而是它没提的反向侧。

本轮实例：评审说「父进程环境变量会让 GUI 留空时仍启用鉴权」。该现象实测属实且非本次引入，但真正该问的是反向——**「GUI 显式设值时，环境变量会不会反向覆盖？**」同环境对拍实测「GUI 值请求 200 / 环境变量值请求 401」，证明 GUI 显式值总是胜出，无覆盖风险。于是处理方式是补文档说死优先级，而不是改代码；若当时直接照评审「修」，反而会破坏环境变量这一有效的高级配置用法。

三个判据：
- **现象属实吗？** 实测复现（本例：401 vs 基线 200）。
- **是我引入的吗？** 追 `git log -S` 定位引入提交与日期（本例：源自改名兼容层，早于本次改动）。
- **反向会不会更糟？** 构造反向输入对拍（本例：GUI 有值时环境能否覆盖）。

三条都答完再决定「改代码 / 补文档 / 不动」。只答第一条就动手，是照单全收。

### 契约测试必须剥离注释再断言

评审常点名某个字符串（如「不得再用 `--api-key` 传参」）。断言代码里不含该字符串时，**先剥离注释**再匹配——注释里写「不要用 --api-key 传参」会造成误判：

```js
const stripComments = (src) =>
  src.replace(/\/\*[\s\S]*?\*\//g, '').replace(/\/\/[^\n]*/g, '');
assert.ok(!/"--api-key"/.test(stripComments(PROXY_RS)), '...');
```

### 修完要锁死，防止以后再退化

评审指出的坑若属架构级（如「整对象覆盖写盘」「共享保存函数回灌」），除代码修复外必须**写进仓库 AGENTS.md 铁律区**并配契约测试，否则下次改同一模块会原样踩回。
