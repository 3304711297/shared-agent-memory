## 9. Windows MCP Process Tree, Lazy Startup & Orphan Teardown Invariant
In Windows, Agent GUIs (Hermes Desktop / ZCode) spawn stdio MCP servers through deep process trees:
`Agent GUI -> cmd.exe -> npx/uvx -> node.exe / serena.exe`.
Because Windows does not cascade process termination to grandchildren upon GUI window close without an explicit Windows Job Object, grandchildren become orphaned background zombies (CPU 0%, but holding 300MB~500MB RAM across multiple restarts).

### Dual-Tier Defense Architecture
1. **Tier 1: Hermes Native On-Demand Lazy Connect & Idle Recycle (In-App Hygiene)**:
   Never run heavy stdio MCP servers in persistent eager mode. In Hermes `config.yaml` (`mcp_servers.<name>`), configure:
   - `lazy: true`: Enables cold-on-demand start. Hermes registers tools at startup from its local schema cache (`cache/mcp_schema_cache.json`) with **zero subprocesses spawned** (0 Node, 0 Serena, 0 Python), achieving instant boot and zero idle RAM. The process is spawned only on the first actual tool call.
   - `idle_timeout_seconds: 60`: If no tool calls occur for 60 seconds, Hermes automatically triggers a clean `recycle`, terminating the stdio subprocess and freeing all memory/handles until the next call.
2. **Tier 2: System-Level Targeted Whitelist Reaper & Agent Guard (Exit Failsafe)**:
   When cleaning up or automating post-exit shutdown, never blindly `taskkill /IM node.exe` (which kills user web servers, Vite, Next.js). Target exclusively verified MCP signatures:
   - Node MCPs: `commandline` matching `chrome-devtools-mcp`, `desktop-commander`, `context7-mcp`.
   - Python MCPs: `serena.exe` and `cmdline` containing `serena`.
   - Implementation: canonical safe reaper at `%LOCALAPPDATA%/hermes/scripts/cleanup_agent_orphans.py`, orchestrated by background daemon `%LOCALAPPDATA%/hermes/scripts/agent_guard.py` (2.5s debounce after all Agent GUIs close). Both run on the dedicated `%LOCALAPPDATA%/hermes/tools/guard-venv` interpreter — **never** on `hermes-agent/venv` (see the interpreter-isolation rule below).
- **Long-lived daemon interpreter isolation (2026-09-21 实证)**: 任何常驻守护/开机自启脚本（`agent_guard.py`、`cleanup_agent_orphans.vbs`、`quota_service.cmd`、Startup 里的 `.vbs`）**严禁**使用 `hermes-agent/venv/Scripts/pythonw.exe`。验证方法：`python -m hermes_cli._scan_venv_blockers` 会扫描「占用 Hermes venv 的 python 进程」，一旦命中就返回 `blocked: true`，桌面端更新随即弹「关闭其他进程以更新 Hermes」——**用户看到更新失败的真凶往往就是这个后门常驻脚本**。本机专用解释器 = `%LOCALAPPDATA%/hermes/tools/guard-venv/Scripts/pythonw.exe`（独立 venv，已装 psutil；`tools/` 在 `.gitignore` 内，不入库）。改完务必跑一次 `_scan_venv_blockers`，`processes` 列表里不应再出现 `hermes-agent\venv` 的守护进程（本会话自身的临时 execute_code runner 会短暂出现，属正常且随轮次结束消失）。
- **Zero Console-Allocation / Zero Focus-Steal (CRITICAL)**: In background supervisor daemons running under `pythonw.exe` (such as `agent_guard.py`), NEVER invoke console executables (`netstat.exe`, `taskkill.exe`) without `CREATE_NO_WINDOW = 0x08000000`. On Windows, running console apps from a windowless process forces the OS to allocate a transient `conhost.exe` host window; even a 10ms transient console creation steals foreground input focus, disrupting active typing and destroying uncommitted IME candidate buffers. Always terminate processes via native `psutil` (`proc.kill()` / Win32 `TerminateProcess`) and query ports via `psutil.net_connections()`.
- **Self-kill guard when matching by command line (2026-09-21 实证)**: `stop_daemon` 用 `"agent_guard.py" in cmdline` 匹配进程时，**会连自己所在的调用链一起命中**——从 git-bash 里跑 `python agent_guard.py stop/restart`，外层 `bash.exe` 的命令行含该脚本路径，`proc.kill()` 直接把调用方 shell 打死，命令以 rc=15（SIGTERM）静默中断、输出为空。修法两条同时上：① 保护集改为「本进程 + 全部祖先 PID」（`psutil.Process(os.getpid())` 逐级 `.parent()` 上溯），只跳过 `os.getpid()` 不够；② 先按进程名白名单过滤（`python.exe`/`pythonw.exe`），避免匹配到命令行里只是**提及**该脚本路径的 shell。验证：`python agent_guard.py restart` 应 rc=0 并打印 `Stopped N`。
