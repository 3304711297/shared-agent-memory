# 看门仓库 404 迁移 SOP（upstream-watch 类巡检）

适用：定期比对上游借鉴仓库的巡检工作流（`tools/upstream-sources.json` + `tools/check-upstream.py` 模式），
当某个被监控仓库返回 404（删库 / 更名 / 转私有）时如何补齐而非简单删条目。

## 1. 先判性质，再找替代

| 现象 | 判定方法 | 处置 |
|---|---|---|
| 仓库 404，但**作者账号仍在** | `GET /users/<owner>` 返回 200 | 列出该账号 `repos?sort=updated`，找**更名/重建**的同源仓库；同作者延续优先于任何第三方 fork |
| 仓库 404 且账号也没了 | `/users/<owner>` 也 404 | 检索同名活跃仓库，记录「唯一有实质代码」的那个，并在 note 注明活跃度风险 |
| 作者账号在、仓库不在 | 用户 repos 列表里没有该项目 | 视为转私有或删除，按同类项目检索替代 |

检索时按 **原仓库的借鉴定位**筛，而不是只看名字：例如原条目吸收的是「三协议适配器」，
就优先选仍明确支持 Chat Completions / Responses / Anthropic Messages 的活跃仓库，而不是同名空壳。

## 2. 迁移不等于换仓库：必须做增量评估

替换 `repo` 后，基线不能"设成新仓库 HEAD 就完事"——那会把新仓库的全部历史静默跳过。先判两者是否有共同历史：

```
GET /repos/<new>/compare/<old_baseline_sha>...<new_branch>
```
- 返回 `ahead_by>0` → 有共同历史，逐条看增量提交；
- 返回 `status=behind, ahead=0` → 新仓库没有超出旧基线的提交，**零增量**，直接换 repo 即可；
- 返回 404 → 无共同历史（fresh migration history / 重建仓库），必须**逐条审查新仓库的可见提交**，
  尤其与既有能力（脱敏词表、风控指纹、协议适配）直接相关的那些。

评估结论无论采纳与否都要写进条目的 `note`：采纳的写明落地文件与测试；未采纳的写明理由
（架构不匹配 / 需实测 / 风险过大），否则下一轮会重复评估。

## 3. 采纳的最小集原则

上游同类项目的提交常是"整段改写 + 一堆连带调整"。只取**能独立成立、有实测证据、影响面最小**的那一项，
例如上游实测记录「两句相邻即 400，插换行或改一句即 200」——就只落地那一句的精确改写，不搬整段改写盾。
改动涉及风控/脱敏时，必须配单测 + 变异验证（把修复改回缺陷形态，测试必须红）。

## 4. 巡检自动收口的反模式

`gh issue list ... 2>/dev/null || true` 会把 GitHub 的 GraphQL 502 伪装成「没有 open Issue」，
于是"自动关闭跟踪 Issue"静默失效、流水线仍是绿的。同一反模式还会让"创建 Issue"步骤
因查询失败而**新建重复 Issue**。

正确形态：查询失败有限重试（3 次），重试耗尽显式 `exit 1`（宁可巡检变红，也不要静默漏关）；
`gh issue create/edit/comment` 也不要挂 `|| true`。契约测试要同时钉住「不得出现 `|| true`」
与「重试耗尽必须失败」两个方向——只钉功能存在（`gh issue close` 还在）抓不到这个 bug。
